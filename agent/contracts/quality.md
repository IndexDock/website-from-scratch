# Quality contract

Publication requires a successful static build, expected routes, working navigation and primary actions, responsive behaviour, zero critical or serious automated axe violations, keyboard and structural accessibility, content integrity, crawlable rendered HTML, crawler access, unique metadata and canonical URLs, sitemap and robots configuration, a client-specific favicon, a working absolute social image, accurate visible-content-aligned structured data, correct FAQ and breadcrumb relationships when used, accessible approved contact controls, no exposed design-review routes, and the configured Starter attribution.

Use sticky navigation by default when it improves a multi-section or multi-page business site, and verify that it does not obscure anchored content. Apply the baseline answer-readiness requirements in `discoverability.md`. Record justified conditional omissions; do not fabricate content merely to satisfy a feature checklist.

Test 320, 390, 430, 768, and 1440 pixel widths across mobile Chromium, mobile WebKit, desktop Chromium, representative Firefox, and representative WebKit.

Both automated tiers run under `prefers-reduced-motion: reduce`: `playwright.config.ts` sets `contextOptions.reducedMotion`, and `scripts/run-lighthouse.mjs` passes Chrome `--force-prefers-reduced-motion`. This is deliberate and must not be removed as redundant, and it must stay set in both. Automated axe reads computed colours, so an element part-way through an opacity transition measures as near-invisible and is reported as a serious contrast failure for text that is solid and readable a moment later. Both tiers run axe — Lighthouse inside its accessibility category — so setting this in only one leaves the other reporting the artefact with nothing to contradict it. Reduced motion measures the end state instead, which is the state a reader sees and the one `agent/rubrics/design-craft.md` already requires every reveal to expose. The consequence is a hard dependency in the other direction: a reveal with no reduced-motion end state hides its own content from the gate, so that end state is a requirement rather than a courtesy.

**Writing a test that asserts on an animation.** Because the suite runs with motion reduced, a test that reads `animation-name`, or any moving value, sees the reduced-motion result and not the animation. Do not delete the animation to make such a test pass — that is the failure this setting exists to prevent. Wrap those tests in a `test.describe` block with `test.use({ contextOptions: { reducedMotion: "no-preference" } })`, and keep it to tests whose subject really is the motion. Anything asserting layout, contrast, or content stays on the reduced-motion default. Note that `test.use` replaces `contextOptions` wholesale rather than merging it. This rule lives here because `agent/phases/implementation.md` has the implementation worker rewrite `tests/starter.spec.ts`, so a note in that file does not survive the rewrite.

## Three tiers, and who owns each

Browser engines cannot be installed inside a cloud agent sandbox: the Playwright download host is not on Claude Code's network allowlist, and Codex has no agent-phase internet. `*.workers.dev` is unreachable for the same reason. The gate is therefore split, and no tier is optional.

- **Tier 1, the agent, offline after `npm ci`.** `npm run validate:agent`: version agreement, project state, status synchronization, Astro diagnostics, production build, release validation and its fixtures, and Cloudflare packaging through `wrangler deploy --dry-run`. Run it before every push.
- **Tier 2, continuous integration.** `npm run validate:milestone` adds Playwright across the five browser projects, automated axe, and Lighthouse. It runs on pushes to the agent's session branches (`claude/**`, `codex/**`, `indexdock/**`), on pushes to `main`, and on pull requests, and it gates promotion to `main`. The agent reads the run result; it does not simulate it or claim its outcome.
- **Tier 3, the learner.** Business accuracy, contact details, tone, imagery, and whether the site represents the business, judged on the live URL. Never ask the learner to detect technical SEO, AEO, schema, redirect, accessibility, or crawler defects.

Live production verification belongs to Tier 2, because only CI can reach the deployed site. A hard requirement is satisfied when its owning tier passes, and by nothing else.

Tier 2 also renders the concept pages published under the design-review routes, before the learner ever opens one. `tests/design-review.spec.ts` discovers whatever concepts the build contains, at the five widths above, and checks each for horizontal overflow, serious and critical axe violations, and that the page really rendered; that spec is the authority on exactly what runs and why, including what it deliberately does not attempt. It skips cleanly when no concepts exist, which is the normal state. These pages are deliberately not held to the Lighthouse targets below or to the full accessibility gate the published site must pass: a review route is a throwaway preview removed before publication, so holding it to publication numbers would stall the learner behind a figure that does not matter. The check is for defects only, and a defect the learner still finds is repaired under `agent/phases/design-review.md` without costing them a revision round.

Homepage and primary conversion page targets are Performance 90+, Accessibility 95+, Best Practices 95+, and SEO 100. Targets do not replace hard requirements, and laboratory results do not guarantee field Core Web Vitals.

`lighthouserc.json` records a lower SEO floor than 100 on purpose. The temporary Starter is deliberately `noindex`, which costs SEO points it cannot recover, so `scripts/run-lighthouse.mjs` applies the relaxed floor only while the built homepage is `noindex` and raises SEO to a required 100 for every indexable client site. Performance is asserted as a warning because it is a target rather than a hard publication gate. Read the runner, not the configuration file alone, when checking which gate applies.
